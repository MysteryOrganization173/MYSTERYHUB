## 3. What could *not* be tested here, and why

This sandbox has **no `.env.local`** — no live Supabase project, Paystack
keys, SuccessBizHub credentials, or Cloudinary account are reachable. That
means the following could not be exercised end-to-end in this session:

- Real sign-up → referral attribution via the DB trigger.
- A real Paystack payment → webhook → commission credit → wallet balance
  update.
- Wallet-funded checkout, withdrawal request → admin approve/reject →
  balance refund.
- Admin panel against real data (suppliers toggle, referral analytics
  numbers, orders/users lists).
- Cloudinary upload script (`npm run assets:upload`) and `CldImage`
  delivery (the code path exists and falls back cleanly to local
  `/public` assets — verified by the HTML above — but was never run against
  a real Cloudinary account).

This is a pre-existing environment limitation, not something introduced by
this pass — the previous V1 foundation had the same gap. Confidence in the
untested paths comes from: the automated checks above, direct HTTP smoke
testing of every reachable route, and manual code review of the money-moving
paths (webhook idempotency via the `referral_commissions.order_reference`
unique constraint; wallet debit-before-credit ordering on withdrawal
rejection; every `/api/admin/*` and `/api/wallet/*` route re-checking auth
independently of the client).

A step-by-step checklist for running these flows once real credentials exist
is in `docs/manual-testing-checklist.md`.

## 4. Condition of the product after this pass

**Before V1.5:** a technically-real V1 checkout/payment/tracking core
wrapped in a homepage that made false claims (a wallet and referral
commission system that had zero backing tables), a dashboard that was a
`ComingSoon` stub, no admin panel at all, and account creation with no
stated value proposition.

**After V1.5:** every claim the homepage makes now has a real, working
system behind it:

- **Wallet** — real balance, full audit ledger, credit/debit, wallet-funded
  checkout, admin-mediated withdrawals. (`supabase/migrations/0003...sql`,
  `src/services/wallet.ts`)
- **Referrals** — real unique codes, real attribution at signup, real
  commission crediting on paid orders, idempotent against duplicate
  webhooks, a real dashboard page with share links and history.
  (`src/services/referrals.ts`)
- **Admin panel** — built from scratch: dashboard stats, orders, users,
  suppliers (enable/priority), withdrawal approvals, referral analytics —
  all independently auth-checked server-side, with a genuinely conditional
  nav link.
- **Supplier architecture** — a real registry reading `supplier_settings`
  instead of a hardcoded adapter, so a second supplier can be enabled by an
  admin without a redeploy (though only SuccessBizHub-live + Mock/Test exist
  today — no fabricated second live supplier).
- **Account creation / sign-in** — a real benefits-led redesign
  (`AuthShell`), referral-aware messaging, and a trust/security line.
- **Dashboard** — personalized, real data throughout (orders, wallet,
  referrals, settings) — no hardcoded zeros or fake stats.
- **FAQ** — one real, shared content source; homepage preview and the full
  page can no longer drift apart.
- **Visual identity** — custom-generated, on-brand hero/banner/OG/empty-state
  imagery, committed to the repo and wired to fall back to local assets or
  upgrade to Cloudinary delivery the moment credentials are configured.

## 5. Payment & security status

- **Payments:** Paystack remains the only live payment rail (server-
  initialized transaction + popup resume, HMAC-verified webhook — unchanged
  from V1, now additionally triggers commission crediting). Wallet payment
  is a genuinely new, real payment path for full-balance orders. Stripe env
  vars remain scaffolded-only, never wired to a real integration — not
  claimed anywhere as live.
- **Security:** every new API route independently re-verifies the caller
  (`getUserFromRequest` for user-scoped routes, `requireAdmin` for admin
  routes) rather than trusting client-side gating alone. All four new
  tables have RLS enabled; three are owner-scoped `select`-only (all writes
  server-side via the service-role client, matching the pre-existing
  `orders`/`profiles` convention); `supplier_settings` has no client policy
  at all. No secret of any kind (Supabase, Paystack, SuccessBizHub,
  Cloudinary) is returned by any response body or present in the client
  bundle — verified directly in this pass.
- **Known, deliberate limitations** (see `docs/product-audit.md` §"Known,
  flagged limitations" for full detail): no cookie-based SSR session
  (bearer-token auth instead); wallet balance updates are read-then-write,
  not wrapped in a DB transaction/RPC (referral commissions are protected
  by a stronger unique-constraint guard, so double-crediting is not
  possible even though this narrower race exists); withdrawals are
  admin-mediated, not automated bank/mobile-money transfer; SuccessBizHub's
  wire format is unverified against real API docs (none exist publicly);
  the 5% commission rate and withdrawal minimum are named-constant
  placeholders, not verified business numbers.

## 6. Remaining blockers to a real production launch

None of these are code defects — they are external configuration/business
decisions out of this pass's scope, same as the pre-existing V1 blockers:

1. Real Supabase project + migrations applied (`0001`–`0003`).
2. Real Paystack **live** secret key (test-mode keys work for a soft
   launch/demo).
3. `ADMIN_EMAILS` set to the real admin's email(s).
4. SuccessBizHub production base URL + API key — and a validation pass
   against real sandbox responses, since the wire format was written
   defensively without public docs.
5. Optional: Cloudinary credentials, then `npm run assets:upload` +
   `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` to move from local image fallback to
   CDN delivery.
6. Running the manual checklist in `docs/manual-testing-checklist.md`
   against that real configuration before public launch.
